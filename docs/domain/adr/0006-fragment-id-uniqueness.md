# ADR-0006: スキーマ断片の登録と ID 一意性

## Context

Parts プラグインは `ctx.parts.addFragment({ parts, assets, slots? })` でスキーマ断片を追加できる（[parts.md](../../plugins/parts.md)）。複数の Parts プラグインが同じエンジンに登録されると、各断片の `id` 同士が衝突しうる。

- `parts.md` は **Part の `id` 衝突をエラー**と明記しているが、**Asset の `id` 衝突**については未定義だった
- 一方で Loader のキャッシュキーは `asset.id` を基本とする（[loader.md](../../plugins/loader.md)）。別 `src` の Asset が同じ `id` で登録されると、**キャッシュの取り違え**など実害に直結する
- 誰が `id` の一意性を保証するのか（コアか、プラグイン作者か）が曖昧だった

## Decision

**`slot.id` / `part.id` / `asset.id` は登録全体でグローバル一意とし、`addFragment` 時にコアが重複を検査する。完全に同一定義の重複は冪等に許容し、定義が食い違う重複は例外にする。**

- 基本スキーマと各 `addFragment` をマージする過程で、コアは各 `id` の重複を検査する
- **完全同一定義**（ディープ等価）の重複は **冪等に許容**する（同じパックを 2 回読み込む、依存で重複登録される等を吸収）
- **定義が食い違う**重複（同じ `id` で `src` や属性が異なる）は **例外**を投げる（`DuplicateIdError` 等、`id` と衝突元を含む）
- **暗黙の後勝ち上書きは禁止**する（silent fallback 禁止の原則に従う）
- 「完全同一定義」の判定は **全フィールド（`x-*` 含む）のディープ等価**を既定とする。より緩い等価規則を将来採るとしても、それまでは保守的にディープ等価で判定する（差異があれば例外）

この方針は既存の「Part の `id` 衝突はエラー」を `slot` / `asset` にも拡張し、全 `id` 種別で統一する。

## Consequences

### 良い影響

- `asset.id` の一意性が保証され、Loader のキャッシュキーが安全になる
- 冪等許容により、同一パックの重複登録や依存の重複に強くなる
- 衝突が静かに上書きされず例外で表面化するため、デバッグが容易（fail loud）
- `id` 衝突の扱いが Slot / Part / Asset で統一され、規約が単純になる

### 悪い影響・トレードオフ

- 「完全同一定義」を判定するための等価比較が必要（`x-*` を含むディープ等価か、主要キーのみかを決める必要がある）
- サードパーティ製パック同士の `id` 衝突は利用者側で解決が必要（名前空間化はしない方針のため）

### 影響範囲

- `@edv4h/alter-ego-core`（PartsRegistry / 断片マージ時の重複検査）
- `docs/plugins/parts.md`（「競合とレイヤー」節に Asset `id` を追記）
- `docs/schema.md`（`id` の一意性に関する補足）

### 追随タスク

- ~~「完全同一定義」の等価判定規則の確定（ディープ等価か、`id` + `src` + `kind` 等の主要キー比較か）~~（全フィールドのディープ等価で確定。[parts.md](../../plugins/parts.md#競合とレイヤー)）
- サードパーティ製パックの `id` 衝突を緩和する仕組み（任意の名前空間プレフィックス等）が必要かの検討
